# Houston v0 — first app live

Houston v0 puts a first app on the internet with nothing app-side but a config file, a CD workflow,
and one secret. An app is a GitHub repo: it declares what it is in a **config file**, builds its
backend image and frontend bundle in a **CD workflow**, and authenticates to Houston with a single
**secret**. On push, that workflow drives a deploy that lands a basic Vite frontend on Cloudflare, a
backend on a dedicated AWS ECS task, and a migrated database schema — all reachable over working DNS
at `<app>.houstonlabs.co`. The deploy is driven entirely through Launchpad's API; v0 has no Houston UI
and no CLI, and the app authors its config by hand.

v0 is the thin vertical slice that proves the whole shape end to end: shared substrate underneath, a
per-app deploy on top, and a real app served over real DNS. Everything Houston adds later —
scale-to-zero, auth, generated UI, capabilities, custom domains — layers onto this spine without
changing it.

## The deliverable

A deploy is **done** when a single push to the app's repo produces, with no manual step:

- **A backend** running as a dedicated ECS task on the shared AWS substrate, serving on the app's API
  subdomain.
- **A frontend** — a basic Vite single-page app — built in CI and published to Cloudflare, served on
  the app's frontend subdomain.
- **A database schema** of the app's own inside the shared Postgres, migrated to the app's current
  version before the new backend takes traffic.
- **Working DNS** on `houstonlabs.co`: the app is reachable at a subdomain derived from its name the
  moment it first deploys, with TLS terminated on both the frontend and the API.

The app author's entire Houston-specific footprint is three things in the repo: the **config file**
(the app's identity, its frontend, and its backend sizing), the **CD workflow** (builds both
artifacts and calls Launchpad's deploy API), and one **secret** (the Houston service credential the
workflow authenticates with). A `migrations/` folder rides along for any app with a schema. There is
no dashboard to click and no CLI to install.

## Platforms and versions

v0 assembles three platform versions. Each is referenced here by what it contributes to the
deliverable; its own docs carry its design and build.

- **`infra/v0`** — the shared substrate every app attaches to: one VPC, one Aurora Postgres cluster,
  one Redis, one ECS cluster, one ALB, the S3 backend that holds Launchpad's per-app Pulumi state,
  and the `houstonlabs.co` zone on Cloudflare. It exports the stack outputs Launchpad reads and creates
  nothing per-app. This version has no design doc yet; authoring `infra/v0/design.md` is the first
  step of the sequence below.

- **`data/v0`** — the logical model over the shared Postgres. v0 exercises only two parts of it: the
  **provisioning path** that creates an app's schema, its `_migrator` and `_runtime` roles, and their
  grants; and the **migration mechanism** that turns an app's `migrations/` folder into applied
  schema under `_migrator`. The rest of the data design — org row-level security, operator-private
  tables, the runtime session-scope contract — is app-runtime concern that a basic v0 app does not
  need, and it does not gate this deliverable.

- **`launchpad/v0`** — the deploy platform that consumes the two CI artifacts and a validated config
  and reconciles them into running per-app infrastructure. v0 builds Launchpad's **baseline deploy
  path**: the config schema and validator, the app registry and deploy API, the per-app Pulumi stack,
  the namespace/IAM/log baseline, ingress routing, the dedicated ECS service, the migration runner,
  the deploy lifecycle with its health gate, the preview-and-namespace safety gate, the frontend
  publish to Cloudflare, and DNS/TLS on the **default `houstonlabs.co` domain only**. v0 also builds
  Launchpad's **MCP control surface** — an operator's way to drive and observe the fleet without a
  UI: listing and inspecting apps and deploys, registering apps, and re-running a deploy over an
  app's existing artifacts. Custom domains and the capability framework are part of Launchpad's
  design but sit outside this deliverable.

## Sequence

The order runs bottom-up: the substrate and the data mechanism Launchpad assumes exist are built
first, then Launchpad's own slices in the order its `implementation.md` fixes.

**Phase 0 — the foundations Launchpad assumes.** These unblock Launchpad's Pulumi and migration
slices and can proceed in parallel with Launchpad's first, infra-free slice.

1. **Repo and tooling skeleton** — the Python monorepo Launchpad, data, and infra are built in.
2. **`infra/v0`** — author its design, then stand up the shared substrate and export its stack
   outputs. Launchpad's per-app stack reads these; nothing above it runs until they exist.
3. **`data/v0` provisioning and migration mechanism** — the schema-and-role provisioning path
   Launchpad's namespace slice calls, and the Alembic-in-process migration mechanism its migration
   runner invokes.
4. **The app artifact model** — the exact shape in which CI hands Launchpad the backend image, the
   frontend bundle, and the config. Settled before Launchpad's deploy API, which consumes it.

**Phase 1 — Launchpad v0.** Built in the order `launchpad/v0/implementation.md` fixes. The config
schema and validator depend on nothing and can start immediately; the Pulumi stack depends on
`infra/v0`; the namespace and migration slices depend on `data/v0`. The **first end-to-end deploy**
lands at the migration runner — a real app served over `houstonlabs.co`. The remaining slices — health
gate, safety gate, frontend publish, and DNS/TLS on the default domain — harden that into the full
v0 deliverable.

## Out of scope for v0

Deferred to later deliverables, each named where it belongs:

- **Custom domains** — v0 serves every app on a `houstonlabs.co` subdomain only. App-declared domains
  are a Launchpad slice held back to a later version.
- **The Houston UI** — no dashboard. An operator interacts with the fleet through Launchpad's MCP
  control surface, not a rendered UI; the `ui` platform is not part of v0.
- **The CLI** — app config is hand-authored and registration is a direct API call; the `cli`
  platform's scaffolding and shared-code delivery are not part of v0.
- **Auth** — v0 launches an app; it does not stand up that app's end-user login. The `auth` platform
  is out.
- **Cryo** — v0's runtime is Launchpad's dedicated task per app, not the scale-to-zero shared pool.
- **Capabilities** — email, object storage, and secrets are Launchpad's capability framework, held
  back; v0 apps get the baseline only.
- **Observability and app deletion** — where a task's logs and metrics go, and tearing a namespace
  down, are open in Launchpad's own design and remain so through v0.
